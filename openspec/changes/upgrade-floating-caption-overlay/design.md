## Context

悬浮字幕窗口由 `src/App.tsx` 的 `FloatingCaptionWindow` 渲染，通过 URL 参数 `window=floating` 与主工作台共用同一个 React 入口。主窗口按 active cue 生成 `FloatingCaptionState` 并经 `floating-caption:update` 送到主进程，主进程再广播给悬浮窗。

三个体验问题的成因分别是：控制入口只存在于主窗口工具栏；`.floating-source` 与 `.floating-translation` 上的 `-webkit-line-clamp: 1` 与 `max-height` 配合 200px 固定窗高造成截断；悬浮窗以 `backgroundColor: "#020617"` 创建且未开启 `transparent`，CSS 又绘制了不透明渐变底。

数据链路本身不截断字幕文本，`getTranslatedCaptionText` 返回的是完整译文，因此第二个问题完全是展示层约束。

## Goals / Non-Goals

Goals：

- 悬浮字幕可独立控制翻译的开始与暂停。
- 当前句在悬浮窗内完整可读，窗口高度随内容变化。
- 悬浮字幕默认不绘制背景板，并可切换鼠标穿透。
- 用户在悬浮窗内的显示偏好不被字幕刷新覆盖。

Non-Goals：

- 不改变 ASR、翻译、润色的调度策略与延迟预算。
- 不在悬浮窗内引入来源选择、语言切换、历史或诊断面板。
- 不新增偏好的跨会话持久化存储。

## Decisions

### 内容与偏好分离

主进程分别保存字幕内容与悬浮窗偏好，广播时合并。`floating-caption:update` 只写内容字段，新增的 `floating-caption:set-preferences` 只写 `locked`、`mousePassthrough`、`backdrop`、`opacity`、`fontScale`。

理由：原实现让主窗口在每次字幕更新时重述全部字段，而悬浮窗的本地调整从不回流，导致偏好被持续覆盖。分离后同时消除了 floating 到 main 再广播回 floating 的回声。合并与归一化逻辑放在 `electron/floatingWindowLayout.ts` 的纯函数中以便直接测试。

### 高度自适应而非固定窗高

悬浮窗渲染进程用 `ResizeObserver` 观察内容高度，经 `requestAnimationFrame` 合帧、并在与上次请求相差小于 4px 时跳过，再通过 `floating-caption:resize` 通知主进程调整窗口高度。

高度上限取工作区高度的 60%，下限 88px。锚边按窗口中心落在工作区上半还是下半决定：下半固定底边向上生长，上半固定顶边向下生长，这样用户把悬浮窗拖到任意位置后生长方向都符合直觉。

由于宽度不参与该过程，改高不会引起重新换行，因此不存在测量与调整的反馈循环。行数限制仍以放宽后的 `-webkit-line-clamp`（源文 3 行、译文 6 行）兜底，确保任何极端输入下都不出现滚动条。

### 固定行预留与只涨不跌的收缩

单纯的高度自适应会带来新问题：流式译文逐 token 增长，窗口跟着一行一行跳，下一句开始时又缩回去，观感上就是字幕在闪。

因此每一行预留固定行数：上一句 1 行、源文 2 行、译文 3 行，用 `min-height` 表达为 `line-height x 行数`。透明窗口下未用满的预留区域完全不可见，所以预留空间不产生视觉代价。实测 620px 宽度下该预留对应 302px 窗高，空状态、短句和典型两行译文全部维持在 302px，只有需要第四行译文的长句才会涨到 332px。三档预留宽度的初始窗口高度也按实测值写入 `getFloatingWindowSize`，避免开窗后立刻自我调整一次。

字幕行块改为顶部对齐。原先的居中对齐会让新增行把已有文字整体上推，第一行位置持续移动；顶部对齐后第一行固定，新行只在下方出现。

超出预留时的调整策略由 `src/captions/floatingHeight.ts` 的 `planFloatingHeightRequest` 决定：增高立即生效，保证句子不被裁切；降低必须等测量值稳定约 900ms 才应用，期间若再次增长则重新计时。该策略是纯函数，可直接对流式增长、回落、再增长的时序做断言。由于字幕稳定后不再触发 `ResizeObserver`，渲染进程按返回的 `recheckInMs` 自行安排一次唤醒来落地待定的收缩。

字幕行块的行间距不能使用 `vh`：窗口高度本身由该行块的高度驱动，视口相对单位会把自己的调整重新喂回测量，形成振荡。因此改为固定像素。

### 透明窗口与宽度分档

悬浮窗改为 `transparent: true`、`hasShadow: false`、`backgroundColor: "#00000000"`。窗口已是 frameless，满足 Windows 下透明窗口的前置条件。

Electron 文档指出透明窗口不应同时开启 `resizable`，因此关闭拖拽缩放，宽度改由控制条按钮以 80px 为步长分档调整，范围 360px 到工作区宽度减去边距。调整时固定靠近屏幕的那一侧边缘，避免悬浮窗越界或偏离用户放置的位置。移动窗口仍由 `-webkit-app-region: drag` 提供。

背景板改为三档 CSS 类：无背景、淡背景、深背景。默认无背景，文字用深色描边与多层投影保证浅色桌面下的对比度。修订、受限与异常状态从改变边框颜色改为改变状态标签颜色，语义保持不变。

### 歌词式鼠标穿透

锁定即开启穿透，主进程调用 `setIgnoreMouseEvents(true, { forward: true })`。`forward` 使 Chromium 继续接收 mousemove，悬浮窗据此在右上角浮出解锁图标；指针进入顶部命中区时通过 `floating-caption:set-mouse-ignore` 临时收回穿透让点击生效，离开后恢复。

该通道只调用 `setIgnoreMouseEvents`，不改写持久化的 `locked` 偏好，避免锁定状态在鼠标移动过程中抖动。IPC 只在布尔值翻转时发送，鼠标移动本身不产生 IPC。穿透状态下拿不到可靠的 mouseleave，因此以 1600ms 无 mousemove 作为隐藏解锁图标的兜底。

主客户端的解锁字幕与重置位置入口保留，作为平台不支持转发时的恢复路径。

### 后台节流

音频采集定时器、载荷队列泵与翻译调度都运行在主窗口渲染进程。Chromium 会把后台页面的定时器降到约 1Hz，因此主窗口与悬浮窗均设置 `backgroundThrottling: false`，否则用户最小化主客户端只看悬浮字幕时翻译速度反而下降，与本次改动的前提冲突。

## Risks / Trade-offs

- 透明窗口在部分 Windows 环境（DWM 合成关闭）下可能不生效。缓解：保留深背景档，观感回到改动前，验证场景中已记录该回退路径。
- 关闭拖拽缩放会改变用户既有习惯。缓解：高度自动贴合内容，宽度提供按钮分档，移动位置不受影响。
- 高度自适应引入窗口 setBounds 调用。缓解：阈值加合帧节流，且全部发生在悬浮窗渲染进程与主进程，不触及翻译热路径。
- 极长的单句仍可能超过高度上限。缓解：上限取工作区 60%，配合放宽后的行数兜底，优先保证不出现滚动条。
- 固定行预留让短句下方留出空白。缓解：透明窗口下该区域不可见；代价是窗口拖动热区比实际文字大，属于可接受的取舍。
- 收缩延迟意味着一句长句结束后窗口会多保持约 900ms 的高度。缓解：该延迟只影响透明区域大小，不影响文字位置，观感上优于逐句抖动。
